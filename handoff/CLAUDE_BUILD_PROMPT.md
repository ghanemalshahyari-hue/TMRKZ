# تعليمات جاهزة إلى Claude لبناء MOVER

أنت مسؤول عن بناء برنامج مؤسسي فعلي لإدارة المرافق والحجوزات وطلبات الخدمات والموافقات الإدارية. اقرأ ملفات هذه الحزمة كاملة قبل التنفيذ. النموذج `prototype.html` مرجع لتجربة الاستخدام، والمواصفات النصية هي المرجع لقواعد الأعمال.

## النتيجة المطلوبة

مشروع قابل للتشغيل داخل شبكة معزولة، بواجهة عربية RTL، وهوية وصلاحيات فعلية، وقاعدة بيانات دائمة، واستوديو للنماذج والتدفقات، وحجوزات لا تتعارض، واعتماد موثق، وسجل تدقيق، وتكاملات قابلة للإضافة، وحزمة تشغيل Docker واختبارات قبول.

نطاق البناء إداري للمرافق. لا تبنِ تخطيط انتشار أو تحسين تمركز عسكري، أو اقتراحات تكتيكية، أو توصيات توزيع وحدات، أو دمج معلومات عملياتية. لا تطلب بيانات مواقع فعلية لتجربة النظام؛ استخدم مرافق وجهات وأشخاصاً افتراضيين.

## طريقة العمل

1. اعرض ملخص فهمك للمتطلبات ومعرّفات القرارات المفتوحة، ثم ابدأ بما لا يعتمد عليها.
2. افحص المستودع المختار وملفات `AGENTS.md` إن وجدت. لا تستبدل مشروعاً قائماً أو تنسخ بياناته تلقائياً.
3. إذا لم يُحدد مستودع، أنشئ مشروعاً محلياً منظماً. لا تفترض أن أي مستودع عام فارغ هو الوجهة المخولة لنشر بيانات المؤسسة.
4. استخدم المعمارية المقترحة في `ARCHITECTURE.md` ما لم تكشف تجربة توافق موثقة سبباً لتعديلها. سجّل أي تغيير في قرار معماري.
5. اختر إصدارات مستقرة متوافقة للمكونات، وثبّت الإصدارات وصور الحاويات بدقة. تحقق من التوافق بين Spring Boot وFlowable وJDK من مصادر الإصدار الرسمية. لا تفترض أن جمع أحدث إصدار من كل مكتبة يعمل معاً.
6. نفّذ شرائح رأسية مكتملة: واجهة ← API ← صلاحية ← معاملة قاعدة بيانات ← أثر قابل للتحقق. لا تنهِ العمل عند واجهة ببيانات ثابتة.
7. احتفظ بتتبّع المتطلبات: رقم المتطلب، موضع تنفيذه، اختباره، وحالته.
8. عند نقص بيانات تخص مزوداً خارجياً، جهّز واجهة التكامل واختبارات عقدها ووسم «غير مربوط»، ولا تعرض اتصالاً وهمياً ناجحاً.
9. لا تستخدم `eval` أو كوداً يكتبه مدير النظام لتنفيذ شروط النماذج أو التدفقات. استخدم لغة قواعد محددة الأنواع ومقيدة.
10. اكتب اختبارات ذات أثر فعلي، وخاصة التزامن والصلاحيات وإصدارات التدفقات والنسخ والاستعادة.

## ثوابت لا يجوز تجاوزها

- الموقع سجل دائم؛ الطلب والحجز والقرار سجلات مختلفة.
- الطلب البرتقالي لا يمنع الحجز حصرياً. الحجز النهائي ينتج بعد اكتمال الاعتماد فقط.
- آخر فحص للإتاحة وتثبيت الحجز والقرار وحدث سجل المعاملة يتمان بصورة ذرية. لا يكفي فحص واجهة المستخدم.
- عند تعارض اعتمادين على المورد الحصري نفسه والفترة نفسها، ينجح واحد فقط، ويُعاد للآخر خطأ عمل واضح دون إنشاء حجوزات جزئية.
- الطلب يحتفظ بنسخة النموذج والتدفق عند التقديم. نشر إصدار جديد لا يغيّر الطلبات القائمة تلقائياً.
- كل إجراء API وتصدير ومرفق وخريطة واشتراك تحديثات يُفحص في الخادم حسب المستخدم والنطاق، مع عدم إرسال حقول محجوبة أصلاً.
- الجهات للعلم لا تحصل تلقائياً على جميع المرفقات.
- تغيير الانتماء أو انتهاء التفويض يسحب الصلاحية السابقة. لا تعتمد على شاشة مخفية أو JWT قديم وحده.
- قرارات الموافقة السابقة لا تُمحى عند تعديل الطلب أو نقل الشخص.
- وقت الخادم هو المرجع. التخزين `UTC` والعرض `Asia/Dubai` ما لم يتغير إعداد المؤسسة.
- لا يوجد `Vercel` أو خدمة سحابية لازمة لتشغيل الإنتاج. كل الخطوط والبرمجيات والخلفيات والوثائق وعمليات التحقق الضرورية تكون محلية في البيئة المعزولة.
- لا تُسمِّ صورة توقيع أو توثيقاً داخلياً توقيعاً رقمياً بشهادة. قرار نوع التوقيع `D-02` ما زال مفتوحاً.

## مراحل التنفيذ

### المرحلة 1: الأساس

هيكل المشروع، الحاويات، قاعدة البيانات والهجرات، تسجيل الدخول، المستخدمون والعضويات المؤرخة، الجهات والمرافق، الترجمة RTL، التخزين المحلي للمرفقات، بيانات تجريبية، وتشغيل أولي مع اختبارات صحية.

### المرحلة 2: رحلة الحجز المكتملة

إنشاء طلب من الخريطة والنموذج، نماذج بإصدارات، مراجعة وإرجاع ورفض، اعتماد، حجز، منع تعارض ذري، جهات للعلم داخل النظام، مهام تنفيذ واستلام، وسجل تدقيق. أثبت اختبارات `AT-01` إلى `AT-12` قبل التوسع.

### المرحلة 3: التهيئة المؤسسية

استوديو BPMN والنماذج، التوازي والتفرعات والشروط والمهل، التفويض وتغير التبعية، صلاحيات الموارد والحقول والتصدير، استيراد الهيكل والخرائط، وسياسات التعديل والتمديد والإلغاء والإخلاء.

### المرحلة 4: الجاهزية للتشغيل

حزمة تركيب معزولة، سجل تراخيص ومكونات، النسخ الاحتياطي والاستعادة، المراقبة المحلية، اختبارات حمل بقيود معلنة، وإرشادات إدارة وترقية وعودة للإصدار السابق. لا تدّعِ جاهزية تشغيل لمجرد نجاح `docker compose up`.

## التسليم النهائي المطلوب منك

1. المصدر الكامل وهيكل واضح للوحدات.
2. ملفات Docker والتشغيل والهجرات والإعدادات الموثقة دون أسرار مضمنة.
3. اختبارات آلية ونتائجها، واختبار قبول للرحلة الكاملة.
4. توثيق API وقرارات المعمارية والتراخيص.
5. دليل التركيب المعزول والنسخ والاستعادة والترقية.
6. بيان صريح بالمزايا المنفذة والقيود والتكاملات غير المربوطة والقرارات المفتوحة.

ابدأ الآن بالمرحلة الأولى، ولا تطلب إعادة إجابة الأسئلة الثلاثين. استخدم الافتراضات المسجلة ودوّن أي افتراض جديد قبل الاعتماد عليه.
